# CF-03.5B / Phase 04 Migration Verification

## Scope and safety

V003 through V005 were applied only to uniquely named databases in a disposable
PostgreSQL cluster. The running `smart_assessment_ai` application database was
not targeted. Fixture rows, including synthetic review evidence, were enclosed
in a transaction and rolled back. The automated runner drops only the test
databases it creates.

## Migration contents

- V003 adds `taxonomy_catalogs`, `taxonomy_releases`,
  `taxonomy_release_members`, `taxonomy_release_events`,
  `question_mapping_sets`, `question_mapping_set_items`, and `analytics_runs`.
- V003 adds nullable taxonomy release, mapping-set, and analytics provenance to
  test, item, attempt, skill-performance, and competency-profile records.
- V004 adds Question Version review/audit fields; import batches/items;
  `question_patterns`, `question_pattern_versions`,
  `question_pattern_skill_mappings`, and append-only review/event records.
- V004 gives import batches a unique source fingerprint and indexes normalized
  payload hashes for idempotent staging and duplicate detection.
- V005 adds Question Version content hashes and explicit supersession history,
  per-version visual asset provenance/rights evidence, and immutability guards
  for passages, assets, options, and answers.
- The migrations add primary/foreign/composite keys, uniqueness/check constraints,
  supporting indexes, lifecycle triggers, review gates, and append-only event
  protection. Question and taxonomy data are not backfilled or approved.

## Legacy and immutability

New provenance columns are nullable, and the isolated fixture confirmed an old
test version can remain without a release or mapping set. No historical release
IDs were inferred. Release, reviewed/published mapping content, approved
Question Versions/patterns, Question Version content/answer/asset snapshots,
and audit events are protected by database triggers. SHA-256 computation for
Question Version content is application-level; the database validates hash
shape and immutability but does not recompute the digest without a database
crypto extension. As with trigger-based protections generally, a database owner/superuser can
disable triggers; production runtime roles must not own the schema or have
privileges to alter/disable these protections.

Rights evidence is required and recorded for approvals, but the database cannot
establish that an external rights document is legally sufficient. Review and
publication remain human decisions.

## Apply and rollback

Initialize a fresh database from `database/smart_assessment_ai.sql`, then apply
V001 through V005 in order. On an existing database, first verify its migration
history/schema is at V002; do not re-run the baseline schema. V003 through V005
intentionally fail if their target objects already exist. Use
`database/tests/run_migration_tests.ps1` to validate an isolated PostgreSQL
instance.

A failure before commit is transactionally rolled back and was verified using an
injected failure. No destructive down migrations are provided. After a committed
release, rollback must use a verified backup restore or a separately reviewed,
data-preserving corrective migration.

## Remaining gates

- Verification ran on PostgreSQL 18.6; PostgreSQL 16 has not yet been tested.
- Production rollout remains blocked until release identity, test-version
  single-release policy, and legacy backfill decisions are explicitly resolved.
- Database triggers do not replace application authorization, legal rights
  validation, or human approval.
- Corpus mining produced 207 structural candidates from 264 normalized records
  (225 HSA, 39 TSA); all remain pending review with unverified rights. The HSA
  bank currently has no correct answers in those records, preventing Question
  Bank materialization until reviewed answer keys are supplied.
- The migration is ready for isolated backend integration work, not deployment
  to `smart_assessment_ai` or production.
